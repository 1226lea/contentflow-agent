# 评估用例编写指南

用例都写在 `cases.json` 里。里面已经有 5 条示例，id 以 `example-` 开头，是我写的。请你检查一遍，不同意的地方直接改，然后照着格式补到 **25–30 条**。

## 每条用例的格式

```json
{
  "id": "c06",
  "type": "synonym",
  "text": "用户会怎么说，就怎么写",
  "expected": ["Strategy Name 1", "Strategy Name 2"],
  "note": "可选：为什么这样标注"
}
```

- **text**：假装你是一个真实用户在聊天框里打字，口语化、可以不完整，**不要照抄下面方向说明里的词**。
- **expected**：你认为“推荐了就算对”的方向，1–2 个，名字要和下表的英文名**一字不差**。
  - 只有一个明显正确的方向，就只写一个；两个都合理，就写两个。
  - 期望模型先追问、不直接推荐的用例，写 `[]`。
- **type**：用例类型，用来分析结果。

## 用例类型和建议数量

| type | 含义 | 建议数量 | 例子 |
|---|---|---|---|
| `clear` | 信息完整、表达直接 | 6–8 | “我会剪辑，喜欢旅行，想做短视频” |
| `synonym` | 口语化或换了说法，和数据里的用词不同 | 6–8 | “爱折腾数码”（数据里是 technology, gadgets） |
| `constraint` | 带约束条件，比如不露脸、时间少、只有手机、预算低 | 5–6 | “不想出镜”“只有手机” |
| `mixed` | 中英混杂，或同时符合几个领域 | 3–4 | “想做 vlog 分享 study routine” |
| `vague` | 信息太少，正确做法是先追问 | 3–4 | “我想当博主，做什么好？” |

**最有价值的是 `synonym` 和 `constraint` 两类**：它们最能看出“理解”和“关键词匹配”的差别。也可以多写几条你在媒体行业见过的真实情况。
